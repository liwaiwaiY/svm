# 实验方案：按被测机制组织（v6）

日期：2026-08-18
定位：实验按**被测机制/结构点**组织，而非按设备（blk/crypto）划分。Micro 每个机制选最能暴露其行为的负载做参数扫描；Macro 与 Application 验证参数选择在混合事务/真实应用下的端到端有效性。配套的环境操作/代码状态见旧文档（`2026-08-18-实验规划与stub断连调试.md`）。

---

## 1. 总览：三类实验的关系

```
Micro（单机制，受控，参数扫描）  →  产出每机制参数选择
        ↓（选定 zc 阈值 / worker 数 / 窗口大小）
Macro（组合机制，混合事务 TPC-C）  →  验证参数在端到端是否成立
        ↓（确认最优配置）
Application（真实应用 PySpark+MySQL）  →  验证机制优化的应用层收益
```

- **Micro**：一个实验只动一个机制参数，负载受控、结果可解释（M1-M5）。
- **Macro**：不动参数，用 M1-M3 最优配置跑混合事务负载，验证"单机制结论叠加后整体成立"。
- **Application**：真实应用端到端 wall time，出最终对比结论。

---

## 2. 公共设定

- 系统：
  - **KVM**：`exp/local/kvm` 本地设备基线
  - **SVM-***：local QEMU + remote stub（TCP loopback）
- 固定：smp=4、virtio-blk num-queues=4（=vcpu 数）、VR_DEBUG=0 二进制、每配置重启环境、fio numjobs=4
- 指标：KIOPS / MiB/s、TPS、时延 p50/p99/p99.9、cpu(usr/sys)、SVM 附加 TCP 段数/重传
- 口径：**KIOPS 与 bs 反比**（KIOPS≈带宽/bs），同 bs 比 KIOPS、跨 bs 比 MiB/s；bs 同时决定是否触发 zc（total≥阈值）
- 结论登记：每次实验后把参数选择写入本文档"结论"小节，供 Macro/App 引用

# 第一部分 Micro：单机制参数扫描

## 3. 机制与负载的对应关系（设计原则）

| 机制（结构点） | 扫描参数 | 选择负载 | 选择理由 |
|---|---|---|---|
| M1 ZC 启用阈值 | `ZC_SEND_MIN` | **crypto**（openssl speed） | 同步路径每请求串行，固定开销占比主导 → 放大 zc 代价 |
| M2 Worker 池 | `VIRTIO_REMOTE_WORKERS` | **blk**（fio 多 job） | 异步多队列并发 → 放大 vq→worker 映射/竞争 |
| M3 Inflight 深度 | 窗口大小 | **blk**（fio iodepth 扫描） | 窗口=流水线深度，与 guest 队列深度直接匹配 |
| M4 Batch 阈值（待实现） | 批上限 N / 字节 M / 超时 T | **blk**（fio 小 IO） | 小 IO 每请求 syscall 与 TCP 段占比最大 |
| M5 Buffer 池化（待实现） | 池尺寸/分桶 | **blk**（fio） | stub 侧分配/释放最频繁处 |

## 4. M1：ZC 启用阈值（负载：crypto）

- **目的**：确定"何时该启用内核 MSG_ZEROCOPY"的阈值策略；小请求走 copy、大请求走 zc 的代价/收益曲线。
- **变体**：`ZC_SEND_MIN` ∈ {0, 4K, 512K}（全 zc / 默认 / 全 copy；可加 16K、64K 细化）
- **负载 A（主，crypto）**：guest 内 `openssl speed -evp aes-128-gcm`，**必须走 virtio-crypto**（afalg 引擎）
  - 块大小：512B / 4K / 64K / 1M（同步路径每请求一块）
  - 矩阵：KVM × SVM-0zc × SVM-4Kzc × SVM-512Kzc，各 × 块大小
- **负载 B（辅，blk）**：fio bs 扫描 4K/64K/1M × 四负载（验证 bs 与 zc 阈值的交互）
- **指标**：MB/s（crypto）、KIOPS+MiB/s（blk）
- **产出**：zc 阈值选择 + "阈值 vs 请求大小"曲线
- **结论**：（待填）

## 5. M2：Worker 池（负载：blk）

- **目的**：vq→worker 哈希映射的并发模型——workers 数与 vq 数匹配时的竞争/并行收益。
- **变体**：`VIRTIO_REMOTE_WORKERS` ∈ {1, 2, 4}（4vq % 1 = 全部共享 1 个 worker；% 4 = 一一对应）
- **负载**：fio randread / randwrite / seqread / seqwrite，**bs=4K 固定**，numjobs=4
- **矩阵**：KVM × SVM-1worker × SVM-2worker × SVM-4worker
- **指标**：KIOPS + clat 百分位 + cpu
- **产出**：worker 数选择（跨 vq 共享竞争的开销曲线）
- **结论**：（待填）

## 6. M3：Inflight 深度（负载：blk）

- **目的**：流水线深度——窗口大小与 guest 队列深度的匹配关系（窗口 < guest 总深度 → backpressure 节流）。
- **前置代码改动**：把窗口大小与 `vring.num` 解耦为独立参数（当前 `pow2ceil(vring_num)` 硬编码=256）
- **变体**：窗口 ∈ {64, 128, 256, 512}
- **负载**：fio **iodepth 扫描** {8, 32, 64, 128} × bs=4K × numjobs=4（guest 总深度=4×iodepth）
- **矩阵**：KVM × SVM-窗口变体 × iodepth 变体
- **指标**：KIOPS + clat p99（节流时的时延上升）
- **产出**：窗口大小选择（窗口 ≥ 4×iodepth 时流水线打满、< 时受限的曲线）
- **结论**：（待填）

## 7. M4：Batch 阈值（待实现代码，负载：blk）

- **目的**：每次 sendmsg 装几个请求/响应——syscall 与 TCP 段数 vs 延迟的权衡。
- **实现**：响应侧攒批合并（凑满 N 或 M 字节即发，TCP_CORK/MSG_MORE），发送侧批量 pop+单 sendmsg
- **变体**：无批 / 批上限 N ∈ {4, 8, 16}、字节 M ∈ {32K, 64K}、超时 T ∈ {0, 50us, 100us}
- **负载**：fio 四负载 bs=4K（小 IO 每请求开销占比最大）
- **矩阵**：KVM × SVM-batch(N,M,T)
- **指标**：KIOPS + `nstat TcpSegsOut` + sendmsg 计数（strace -c）+ clat p99（低负载 iodepth=1 尾延迟）
- **产出**：批参数选择（吞吐↑ vs 尾延迟↑ 的权衡曲线）
- **结论**：（待填）

## 8. M5：Buffer 池化（待实现代码，负载：blk）

- **目的**：stub 侧每请求分配/释放的开销（out 拷贝缓冲、in 数据缓冲、小壳 arena）。
- **实现**：stub 侧 per-vq 分级 slab 池（4K/16K/64K 桶），小壳合并单次分配；**zc 场景归还挂在完成通知**，而非 send 返回即还
- **变体**：malloc（现状）vs 池化
- **负载**：fio 四负载 bs 4K/64K（小 IO 分配最频繁）
- **指标**：KIOPS + 分配次数（perf）+ clat
- **产出**：池化收益（IOPS 提升与分配占比下降）
- **结论**：（待填）

# 第二部分 Macro：组合机制验证（TPC-C）

## 9. Macro 定位与设计

- **目的**：不扫参数，用 M1-M3 最优配置跑**混合事务负载**，验证"单机制结论叠加后整体成立"，并暴露参数之间的交互（如窗口大小与事务并发、worker 数与多 vq 并行）。
- **为什么是 TPC-C**：标准 OLTP 混合事务（读+写+事务等待），IO 特征贴近真实（小随机 IO + redo/log fsync 密集），能综合压 inflight 深度、延迟与 worker 并行度。
- **工具**：sysbench-tpcc（纯 SQL 五类事务：new order / payment / order status / delivery / stock level）
- **数据库**：MySQL 为主（与 Application 复用环境，sysbench-tpcc 在 MySQL 上最成熟）；备选 PostgreSQL

## 10. Macro 实验设计

- **部署**（guest 内，数据落 /data 的 ext4）：
  1. 安装 MySQL 8 + sysbench + sysbench-tpcc（Percona 实现）
  2. 建库建表 + `tpcc_load`（或 sysbench `prepare`）初始化数据
- **参数**：warehouse=4（~400MB 基础数据，10G 盘余量充足；可加 8 档）；并发 threads=4；time=60s；report-interval=10s（取稳定段）
- **矩阵**：
  - 主：KVM × SVM-最优配置（M1-M3 结论）
  - 附：SVM-次优配置（如 M3 未选窗口）对照，验证参数敏感性
- **指标**：TPS、事务时延 p50/p99、DB 侧 IO（iostat）/进程 CPU、SVM 附加 TCP 段数
- **数据点**：每配置重复 3 次取中位数
- **产出**：KVM vs SVM 的 TPS/时延对比 + 参数敏感性结论

# 第三部分 Application：真实应用验证（PySpark + MySQL）

## 11. Application 定位与设计

- **目的**：真实大数据应用端到端验证——机制优化对"完整应用 wall time"的收益，是最终结论。
- **为什么是 PySpark + MySQL**：一个真实 ETL 工作流，IO 特征分阶段（MySQL 读、shuffle 写/读、结果写回），同时覆盖 blk 与 CPU，能体现 remote 机制在真实负载下的整体开销占比。
- **资源约束**（4vcpu / 4GB / 10G 盘）：数据量、分区数、内存需裁剪，见 §12 参数。

## 12. Application 实验设计

- **工作流**（guest 内）：
  1. MySQL 数据落 /data（blk 盘）：数据表 1-2GB（如从 TPC-C 初始化表生成或自建订单表）
  2. PySpark `local[*4]`：JDBC 读表 → 变换（过滤/聚合/join）→ shuffle → 写回 /data（Parquet/CSV）
  3. 可选：读回校验
- **参数**：
  - 数据规模：1-2GB
  - Spark：master=local[4]、driver+executor 内存合计 ~2.5GB（MySQL 留 ~0.5-1GB，`innodb_buffer_pool_size=256M`）
  - 分区数：读分区 4、shuffle 分区 4（匹配 vcpu）
  - 输出：Parquet 单份
- **矩阵**：KVM × SVM-最优配置（M1-M3 结论）
- **指标**：端到端 wall time（重复 3 次取中位数）+ 分阶段耗时（MySQL 读 / shuffle / 写回）+ cpu
- **风险与裁剪**：内存不足 → 减 shuffle 分区/数据量；shuffle spill 过多 → 降数据规模
- **产出**：KVM vs SVM 应用完成时间对比（含分阶段占比，定位开销在哪个阶段）
- **结论**：（待填）
