# M1 / M5 实验结果 —— Bandwidth 汇总

- 日期：2026-08-25
- 后端：SVM blk + null_blk（/dev/nullb0），W=4, B=16, workers=4
- 负载：fio randrw 7:3（70% 读 / 30% 写），iodepth=64，direct=1，runtime=30s，每档 1 次
- bs：16K / 64K / 256K / 1M / 2M（4M 会卡死：1026 descs > 1024 限制，故排除）
- 单位：MiB/s = iops × bs / 2^20；原始 iops 见 `exp/results/m1m5/<tag>/rep1/bs<bs>.json`
- 说明：单次 30s 运行，档间存在明显方差（见结论），未复跑

## M1 —— zc 阈值扫描（I=256, P=on）

| bs | zc=0（全 zc） | zc=64K | zc=4M（全 copy） |
|---|---|---|---|
| 16K | 428.1 | 501.9 | **536.4** |
| 64K | 1021.2 | 1117.4 | **1120.5** |
| 256K | 1974.2 | 1510.7 | **2324.1** |
| 1M | 2482.6 | 2285.8 | **3672.6** |
| 2M | 2480.8 | 2334.6 | **3950.2** |

（总带宽 = read + write）

分读/写：

| bs | zc=0 read / write | zc=64K read / write | zc=4M read / write |
|---|---|---|---|
| 16K | 299.4 / 128.6 | 351.3 / 150.7 | **375.5 / 161.0** |
| 64K | 714.2 / 307.0 | 781.2 / 336.2 | **783.5 / 337.0** |
| 256K | 1382.1 / 592.1 | 1058.1 / 452.6 | **1626.1 / 698.1** |
| 1M | 1737.3 / 745.3 | 1600.9 / 684.9 | **2574.8 / 1097.8** |
| 2M | 1738.0 / 742.8 | 1635.2 / 699.4 | **2768.1 / 1182.1** |

### M1 结论
1. **全 copy（zc=4M）在所有 bs 上总带宽最好或持平**。大块收益显著：
   - 1M：3672.6 vs 2482.6/2285.8（+48% / +61%）
   - 2M：3950.2 vs 2480.8/2334.6（+59% / +69%）
2. **大块下 zc 反而不如 copy**：2M 时全 zc 读带宽仅 1738 MiB/s，全 copy 达 2768 MiB/s（+59%）。zc 的页注册/注销开销在大请求上超过 copy 的 memcpy 成本（null_blk 响应即时，无盘延迟掩盖）。
3. 小块 16K：全 zc 最低（428.1），copy 高 25%（536.4）——与 crypto 侧"ZC 阈值无影响"结论不同，blk 数据路径上 zc 对小块也有 ~20% 拖累。
4. ⚠️ **256K 档异常**：zc=64K 时 256K 应走 zc（≥64K 阈值），但其带宽 1510.7 明显低于 zc=0 的 1974.2，两档同为 zc 却差 30%——疑似单次运行方差，需复跑确认。

## M5 —— inflight × buf_pool（zc=1M）

总带宽（MiB/s），每格 `P=off / P=on`：

| bs | I=64 | I=32 | I=16 |
|---|---|---|---|
| 16K | 355.3 / 353.0 | **480.0** / 358.6 | 361.1 / 354.1 |
| 64K | 809.6 / 693.4 | 905.4 / 876.0 | **1364.2** / 764.0 |
| 256K | 1787.8 / 1590.7 | **2637.2** / 1925.0 | 2299.9 / 2112.9 |
| 1M | 3356.5 / 3384.8 | **4753.6** / 3397.2 | 4324.4 / 3985.4 |
| 2M | 4128.4 / 4017.7 | **4928.9** / 4230.2 | 4461.6 / 4466.7 |

### M5 结论
1. **P（buf_pool）无一致差异**：on/off 差值多在 ±10% 内，且方向不统一（如 64K: i16 的 off 比 on 高 78%，但 1M/2M 基本持平）。可判定 buf_pool 不是带宽瓶颈。
2. **I 效应不单调、不干净**：
   - i32_p0 在各 bs 上普遍偏高（16K 480.0、256K 2637.2、1M 4753.6、2M 4928.9），高于 I=64；
   - i16_p0 的 64K 高达 1364.2（约为 i64_p0 的 1.7 倍）；
   - 与"窗口越大带宽越高"的理论预期矛盾。null_blk 响应在 µs 级，RTT 极小，in-flight 窗口本不应成为瓶颈 → 这些峰谷主要是**单次运行方差**。
3. **大块带宽趋于 4–5 GiB/s**：2M 各档总带宽 4.0–4.9 GiB/s，接近该负载形态下的协议/复制开销上限。

## 关键对比速览（总带宽 MiB/s）

| bs | 全 copy（M1 z=4M） | 全 zc（M1 z=0） | M5 最佳（i32_p0） |
|---|---|---|---|
| 16K | 536.4 | 428.1 | 480.0 |
| 64K | 1120.5 | 1021.2 | 905.4 |
| 256K | 2324.1 | 1974.2 | 2637.2 |
| 1M | 3672.6 | 2482.6 | 4753.6 |
| 2M | 3950.2 | 2480.8 | 4928.9 |

- 全 copy 在小块（16K/64K）最优；大块上 M5 的 i32_p0 略高于 M1 全 copy，但两者差距在方差范围内。
- **方向性结论（相对可信）**：blk 路径下 zc 阈值应调高（≥4M 即全 copy），避免大块走 zc。
