## 1. 项目一句话定位

研究 **SVM（本地 QEMU + 远程 stub 双进程虚拟化）相对原生 KVM 的存储 IO 折损**：
- SVM = local QEMU + remote stub，TCP `127.0.0.1:5552`；数据盘 virtio-blk-pci（vq 数 = smp.cpus = 4）。
- 对照四协议：**KVM**（本地 virtio-blk）、**SVM**（remote stub）、**NVMe-oF**（nvmet→loop(direct-io)→fio.raw）、**iSCSI**（LIO block→loop(direct-io)→data_iscsi.raw）。
- 核心问题：SVM 相对 KVM 到底慢多少、在哪慢、能不能修——已有完整实验矩阵（M1~M6 + Macro + App）。

## 3. 方法论铁律（所有结论的前提，写论文必须引用）

1. **盘相位 ±55%**：跨时段对比必须**同日背靠背 + host/guest 双 drop_caches + O_DIRECT**，任何跨日数值直接比较不可信（macro-b 实证：KVM-b 227/315/444 vs 8/24 的 262/371/481，低 13%）。
2. **禁 page cache**：fio direct=1、virtio-blk `cache=none`、nvmet loop direct-io、LIO block direct-io。**旧 KVM 基线 382K 是 page cache 假象，作废**。
3. fio 口径：60s 稳态、time_based、libaio、randrw=70/30 bs=4K（除非注明）。
4. 结论只取 **8/24 后重做版**（8/24 前数据仅方法学对照）。

## 4. 架构关键机制（改代码/看代码时）

- **worker pool**：vq 按 `vq_nr % workers` 哈希到 worker（virtio-remote.c L1057）。
- **inflight_size（I）是窗口，按请求计数**：吞吐 = 在途/RTT（Little's law）；窗口 = pow2ceil(I)，iodepth>I 被封顶为 I/RTT。
- **batch 触发 = `n_batch>=batch_n || batch_bytes>=batch_m`**（L2345）；默认 batch_m=64K 只装 ~15 个 4K 请求。
- **stub_queue_max（Q）**= req_queue 上限 = 设备 aio 并发上限（Q=1 即无批）——**recv batch 是决定性因素**（10× 跳变）。
- **stub_merge_m（M）**（默认 0=关）：>0 且请求总字节 ≤ 阈值时，把 elem 内多个 4K in_sg 合并为单次大 aio（wire 响应只有 data_len，local 端零改动）。
- send 是真批（sendmsg 合并 iov，zc 单独发），recv 无 syscall 级批（逐 recv()）；stub 设备驱动层是动态批。
- 修改代码位置：`local_qemu/hw/virtio-remote/virtio-remote.c`、`virtio-crypto.c`、`virtio.c`、`vr.conf`。
- 档位矩阵：t0（W=4/I=32/B=16）、t4（W=1）、t5（W=2）；zc_send_min=1MB。
- RTT 注入：host lo `tc qdisc add dev lo root netem delay Xus`（单向），RTT=100+2X；**必须环境就绪后再注入**。

## 5. 实验结论速查（直接可写进论文的数字）

### 5.1 纯 IO（M 系列）
| 实验 | 结论 | 关键数字 | 数据目录 |
|---|---|---|---|
| **M2G**（权威） | W=1 是唯一干净瓶颈；SVM 相对 KVM 唯一真实损失 = **seqrd -36%** | 随机读域 W=1 掉一半 | `m2g/` |
| **M3RTT3** | 吞吐 = 在途/RTT；窗口减半 → 全 RTT 域吞吐减半 | 高 RTT 端"吞吐=在途/RTT"成立 | `m3rtt3/` |
| **M3 三协议** | 高 RTT 端四协议收敛同一曲线（2ms ≈14-15K vs 理论 16K）；低 RTT 端 iSCSI(61K)≈KVM(69K)>SVM(53K)≈NVMe-oF(48K) | — | `m3net2/` |
| **M4 batch** | send batch 无净增益（在途不变） | batch 1/16/32 × iodepth 1~128 全噪声内 | `m4new/` |
| **M4B** | local send batch 是二阶优化 | L≥16 把 τ 8.1us→7.4us（-8%），L=16 饱和 | `m4local/` |
| **M6** | **recv batch（Q）是决定性因素** | Q=1→7.2K（严格串行）；Q≥16→55-77K（10×）；Q64/I128/d64=92.2K | `m5/q1~q64/` |
| **M5 merge** | merge+buf_pool(P) 大块有效；带宽占比随 bs 缩 | P=on：1M +35%、2M +22%、256K +11%；≤64K 噪声级 | `m5/` |
| **M1 内存** | SVM 恒定 +5~10%（iodepth=1 权威版）；在途缓冲=在途×bs | 旧"+14→81% 随 bs 涨"是堆积假象 | `m1mem/` |

完整模型：**吞吐 ≈ min(盘(min(在途,Q)), 协议(min(在途,I), slack))**；slack=I−N。

### 5.2 Macro（sysbench TPCC，MySQL datadir 在数据盘 vdb）
- **8/24 重跑**：SVM 相对 KVM **-32/-35/-29%**（threads 1/2/4，txn/s 10782/16459/22360 vs KVM 15139~29464），avg/p95 延迟劣化同向。
- **8/25 四协议同日锚点（权威）**：KVM-b 227/315/444；SVM-b **-19/-37/-38%**（183.9/197.1/275.8）；NVMe-oF -30/-31/-38%；iSCSI **-47/-31/-44%**（119.4 最低）。
- 结论：SVM≈NVMe-oF，iSCSI 恒最低；"约三成"折损随盘相位在 20~40% 漂移。

### 5.3 App（Spark pagerank / ALS / xgb）
| 实验 | 形态 | SVM vs KVM | 结论 |
|---|---|---|---|
| **pagerank 四协议**（9.1） | 计算主导（IO 总 ~400-500MB 突发） | 无差距（<2%） | SVM 折损只在 IO 密集+延迟敏感下显形 |
| **pagerank @150us**（9.2） | 同上 | 无差距 | **SVM RTT≥200us 确定性卡死**（根因未定位），150us 是可用上限 |
| **ALS 9.3**（逐行解析） | CPU 解析主导 | 无差距 | build 是 Python 解析瓶颈非 IO |
| **ALS-IO 9.4**（pandas 向量化） | 真 IO 密集、一次性顺序大块加载 | SVM 追平（c4 build 10.3 vs KVM 10.1s） | 顺序大块+高并行下 SVM≈KVM；iSCSI c4 **+162%** |
| **ALS-BIN 9.5**（每 iter 强制重扫 2.4GB） | IO 密集+延迟敏感 | total **+9~23%**（train 段 +9~22%） | 折损集中在逐 iter 重扫；build 并行读 SVM c4 反超 KVM（9.38s 四协议最快） |
| **xgb 先导 9.6**（1.4GB 一次性） | 解析/计算主导 | 收敛（c4 train +21%） | IO 不进关键路径 → 不显形 |
| **xgb 正式 9.6**（6M 行 1.66GB，16 rounds 强制重扫） | 真 IO 密集 | total **+8.4/+13.9/+15.9%**（c1/2/4）；iSCSI **+75~90%** | train 分层：KVM 44s < NVMe-oF 47s < SVM 50s < iSCSI 84s |

### 5.4 综合结论（论文可用）
1. **SVM 折损的充分条件 = 延迟敏感 × 每 iter 强制重扫（缺页→远程往返逐轮累加）**；一次性顺序大块冷读不显形。
2. 吞吐统一由"在途/RTT"决定（Little's law），batch 不改变在途故无净增益。
3. iSCSI 带宽瓶颈（450~533MB/s）在 IO 密集场景恒为最大短板。
4. 内存开销恒定 +5~10%，非结构性问题。
5. SVM RTT ≥200us App 级卡死（未修复）。
