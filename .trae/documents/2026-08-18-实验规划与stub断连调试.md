### 1.3 实验矩阵设计（Micro / Macro / Application 三层）

设计原则：每个实验都要能对应到 virtio-remote 的具体设计点。

| 设计点 | 对应实验变量 |
|---|---|
| 每 vq 一条 TCP 连接 | `num-queues` 多队列 |
| send/recv worker 池（各 4 个）、vq%4 哈希 | 并发深度、num-queues 扫描 |
| MSG_ZEROCOPY + ZC_SEND_MIN（<4KB 拷贝） | 请求大小扫过 4K 阈值 |
| inflight 窗口（SPSC） | iodepth |
| local 流水线 pop→send→resp→push | 往返延迟、QD |
| ioeventfd 仅 local 启动 | cache/通知路径 |

- **Microbench**：M1 单请求延迟（bs 扫描）、M2 并发扩展（QD=1/4/16/64、num-queues=1/2/4/8）、M3 ZC 阈值（bs=512B~1M）、M4 crypto 吞吐（算法/bs/QD）、M5 链路带宽上界
- **Macrobench**：X1 fio 混合负载、X2 LUKS 加密盘 + fio（crypto+blk 双通道）
- **Application**：A1 SQLite 业务系统（采集+报表，推荐主应用）、A2 Git 仓库操作（commit+gc）、A3 PySpark wordcount、A4 nginx HTTPS（需 afalg，不可用则降级）

对照矩阵：配置 A（本地设备 kvm/ 脚本）vs 配置 B（remote：svm/ + remote/ 脚本）；X2/A1(LUKS 版) 加"明文 vs LUKS"四组交叉。每实验 3 次取中位数；local/stub 绑核；固定镜像、脚本、数据量。

### 1.4 设备 remote 化可行性结论

| 设备 | 数据面 | remote 化结论 |
|---|---|---|
| blk / crypto | 全部走 vq | ✅ 适合（实验目标） |
| net / scsi | 全部走 vq | ✅ 理论上适合 |
| virtio-gpu | vq + 显存 BAR/blob 内存映射 | ⚠️ 命令可转发，但 display 绑死 local、延迟敏感，不现实 |
| virtio-iommu | 纯控制面（attach/map） | ⚠️ 可冒烟证明通用性，无性能负载意义 |
| virtio-pmem / virtio-mem | 内存映射直通，vq 只做控制 | ❌ 数据面搬不走 |

- **virtio-mmio 是传输层不是内存设备**：寄存器走 MMIO 陷阱（VM-exit→KVM→QEMU），vring 数据在 guest RAM 走 EPT 直通。
- **127.0.0.1 通信**走内核 loopback（lo 接口），不经过物理 NIC；QEMU 里是普通 TCP socket，与 virtio-net 无关。
- **GPU 跨机**：MMIO 处分离不可行（陷阱路径无批处理边界 + 显存数据面无法寄存器化）；成熟路径是 API remoting（rCUDA/gVirtuS）。

### 1.5 负载选型结论

- **CIFAR-10 + TensorFlow**：CPU 密集、数据量小、IO 几乎为零、crypto 无关 → 不适合 virtio-remote 实验。guest 无 GPU 直通时 TF 必然回退 CPU。
- **PARSEC**：共享内存多线程 CPU benchmark → 只适合做 CPU 虚拟化基线，不能作为 blk/crypto 负载。
- **PySpark 单机 local 模式可行**：关键 `spark.local.dir` 指向 remote 盘（/data），否则 shuffle 走系统盘、remote 差异被掩盖。`pip install pyspark` 即可。
- 推荐真实应用：**SQLite（IO 密集）+ LUKS 加密盘（crypto 密集）**。

## 2. 本次调试（已解决）：local QEMU 高压 IO 崩溃 —— zc 竞态

### 现象
- guest 内跑 fio 高压负载（randwrite/iodepth=64/4jobs 或 randrw/iodepth=32）时，local QEMU 输出两行后**直接退出**：
  ```
  qemu-system-x86_64: local qemu: no pending elem for seq 5505
  qemu-system-x86_64: local qemu: sendmsg to stub failed: Bad file descriptor
  ```
- 第一行是根因，第二行是**次生症状**：conn_err 路径关闭了 fd，send worker 下一次 `sendmsg` 撞上已关闭的 fd。

### 根因（`hw/virtio-remote/virtio-remote.c`，local 侧 send 路径）
- 旧代码是 **先 `sendmsg`、后 `inflight_publish`**。
- stub 与 local 同在本机（loopback），响应极快：响应头先于槽位发布到达 recv worker → `inflight_lookup()` 找不到该 seq → 报 `no pending elem` → `goto conn_err` → `local_zc_fd_teardown()` 关 fd → `local_conn_lost()` 退出 guest。
- zc 完成通知同样存在此竞态：`sendmsg` 返回后即可被 `local_zc_drain` 匹配到窗口外的 seq。
- 旧代码只覆盖"发布后再发送成功"的路径，没有覆盖 stub 抢答/完成通知先到的窗口。

### 修复（`virtio-remote.c` L1015-1101，commit：本轮未单独提交，已在 `168ebb117 compile` 之后的工作区）
- **`inflight_publish` 移到 `sendmsg` 之前，所有路径统一**（zc 路径与 copy 路径都要先发布）。
- **发送失败回滚**：槽位置为 NULL 空洞（不回退 tail，靠 `inflight_clear` 的洞推进跳过），zc serial 交还 `st->serial`，支持 EAGAIN 回退 `virtqueue_unpop` 重发。
- zc 被拒（ENOBUFS/EINVAL）转 copy 发送时，把预发布的 zc 槽转成普通槽。
- 配套：`local_retry_send` 增加 `ctx->dead` 检查（stub 已挂时不再重注册 fd handler）；recv 侧清槽后 `local_drain_wake` 唤醒 send worker。

### 验证（16:34 含修复二进制，guest 内 fio，ssh wai@127.0.0.1:2222）
| 测试 | 配置 | 结果 |
|---|---|---|
| randwrite（上次崩溃配置） | bs=4k, iodepth=64, 4jobs, 60s | **1,453,694 次写入，0 错误**，BW 94.6MiB/s，QEMU 存活 |
| randrw 混合 | bs=4k, rwmixread=50, iodepth=32, 4jobs, 60s | ~150 万次混合 IO（read+write），**0 错误**，QEMU 存活 |

- local QEMU 日志全程无 `no pending elem` / `sendmsg failed`；inflight 窗口按序推进（seq 到 35 万+）。
- 复现/验证命令：

## 6. 连接与握手流程备忘（调试参考）

- local 主动连 stub：connect 控制口 → 协商（发 src_ports、收 dst_ports，`LOCAL_NEGO_MAGIC`）→ 逐 vq 连接 stub 分配的端口。
- stub 被动：accept 控制口 → 读协商 → 分配 vq 监听端口 → accept 各 vq 连接 → 注册 `stub_distributor`（aio_set_fd_handler）。
- local 连接重试有限（CONNECT_RETRY_TIMES=3），失败报错退出，不会无限循环。
- 每 vq 一条 TCP 连接，请求头 `[vq_nr][seq][out_num][in_num][lens][data]`，响应头 `[vq_nr][seq][len][data]`。
